================================================================================
N=32768, k=2048场景优化策略
================================================================================

【当前状态】
✅ Official: 0.0485 ms (2.62x vs PyTorch)
✅ Optimized: 0.0480 ms (2.65x vs PyTorch)  - 快0.94%（不稳定）
❌ Large-k: 未验证，有correctness问题

【官方DeepSeek V3算法】
基础算法：两阶段Radix Selection
  Stage 1: 8-bit直方图快速分割
    - 处理所有 N=32768 个元素
    - 构建256个bin的直方图
    - 找到包含topk的threshold bin
    
  Stage 2: 迭代细化（最多4轮）
    - 只处理threshold bin的候选元素
    - 每轮使用更高有效位（24,16,8,0）
    - 直到找到准确的topk

【为什么Stage 1不是瓶颈？】
✅ 简单操作：float→uint16(高8bit)→atomic_add
✅ 充分并行：1024线程×N/1024轮
✅ L2缓存友好：顺序访问histogram

【为什么Stage 2可以优化？】
当k=2048时：
  - threshold bin候选数 ≈ 2000-3000个
  - 这些候选需要4轮迭代细化
  - 每轮都要调用convert_to_uint32()
  
🔍 瓶颈分析：
  convert_to_uint32(x) {
    bits = reinterpret(x)        // 1条指令
    if x<0: flip bits; else: OR  // 2-3条指令
  }  // 总共3-4条指令，但延迟较高（float32转uint32）

  在4轮迭代中，同一个候选元素被转换4次！

【Optimized版本的缓存优化】
❌ 问题：缓存的候选集有上限(4096)
   - 当候选集>>4096时，缓存命中率低
   - 重复计算仍然发生
   
❌ 问题：缓存放在Stage 1
   - 只缓存threshold bin的候选
   - 其他候选未被缓存
   - Stage 2从缓存取，但很多不在缓存中

❌ 问题：Bank conflict
   - 1024线程同时访问s_cached_uint32[]
   - 导致shared memory访问延迟

【更好的策略：针对大k优化】

方案A: 增大SMEM_INPUT_SIZE
  优点：更多缓存命中
  缺点：
    - 需要考虑shared memory极限(232KB on H100)
    - 可能增加bank conflict
    - 分支与循环更复杂
  
  估计效果：小改进，不会很明显

方案B: 改进caching策略
  想法：在Stage 2中动态构建缓存
  - 第一轮：处理全部候选，构建缓存
  - 第二轮及以后：从缓存读取
  - 缓存命中率100%（对于存活下来的候选）
  
  挑战：
    - 需要两遍遍历（第一遍缓存，第二遍计算）
    - 同步和内存管理复杂
    - TileLang编译限制

方案C: AutoTune + 自适应选择
  想法：根据k值自动选择算法变体
  - k < 512: 使用Optimized（小k优化）
  - k >= 512: 使用Official（更稳定）
  
  优点：
    - 简单可行
    - 两个版本都稳定
    - 无需新开发
    - 对所有场景都有最优表现
  
  缺点：
    - 无法获得大k的进一步加速
    - 只是"选择合适工具"而不是"优化"

方案D: 内核融合优化
  想法：将Stage 1和Stage 2合并
  - 在Stage 1中直接计算2-4个候选的细化
  - 避免多轮循环开销
  
  难度：非常高，基本上重写算法

方案E: 使用Warp-级原语
  想法：利用H100的warp功能
  - 使用__shfl_down_sync进行warp-level树归约
  - 减少shared memory压力
  - 改善bank conflict
  
  难度：TileLang可能不支持
